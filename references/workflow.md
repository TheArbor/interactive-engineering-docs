# 工程工作流

## 需求 → 设计 → HTML

从问题研究或按已选方向核验时，先走[设计对话工作流](design-dialogue.md)，再把结论、可选项和风险并入下方工程章节。

1. 从已有约束和用户确认中提炼目标、参与者、输入、中间产物、交付结果和当前范围。资料不全时先处理可确定部分，把会改变范围或安全性的决策列出。
2. 从一条端到端主流程开始，标明数据所有权和跨系统交接。补改变结果的失败分支、恢复路径、权限、状态变化和责任方。
3. 用任务所需的最小工程契约支撑实现。展示入口与关键返回、跨实体关联、状态迁移和异常处理。对重复提交、并发、部分完成、版本冲突、老数据及撤销按实际相关性说明。
4. 写验收条件，包含样本、环境、操作、可观察结果。关键未知项给出决定所需证据，如真机耗时、缺页样本或并发重试。文档用方案或候选状态，交互示例标注演示。

组装正文时按「目标与范围 → 核心功能 → 架构和数据 → 操作与异常 → 实施与验收」串起来。实施顺序说明每一步依赖的前置决定、产物和验证条件。用项目导图链接这些章节，再为讲解选一条从目标走到验收的路线。

按两类新读者试读。给业务读者一项主场景，能从首页找出为什么要做、谁参加、各自做什么和最终得到什么。给开发读者同一场景和一个关键异常，能从图与正文找到业务规则、负责组件、状态变化、工具或依赖及恢复办法。找不到的工程信息补到对应章节，尚待确定的工具标为候选或待确认。

## 实现 → HTML

1. 核对目标仓库、分支、项目说明和请求范围。从应用路由、命令、任务入口或已公开接口开始，沿调用、校验、状态修改和持久化追踪。必要时查数据迁移、配置和测试。
2. 从产品入口、主操作和交付物列出核心功能。为每项标出操作步骤、决策规则、输入输出、失败后的行为与源码位置，再据此分配文档章节和图。比如 PDF 命题工作台至少分别追踪章节划分，以及选材、题量规划、生成、审题、补题的出题链路。格式整理按独立模式核对。
3. 用授权的只读操作核实关键行为。无法运行时标注静态核对和仍待验证的点。生产状态只能引用生产证据。
4. 对不一致给出可定位证据和影响。在 HTML 表示当前行为，同时保留已确认但尚未实施的目标。若任务需要维护规格，按项目约定同步受影响的设计或记录。

记录版本或提交、入口、关键实现和样本范围。实验、模拟接口、功能开关、仅有测试的能力注明条件。验收前按核心功能逐项打开成品，检查图、操作与异常是否清楚呈现。通过临时浏览器测试与有真实数据的联调分别取证。

## HTML → 规格、任务或实现

1. 以当前 HTML、相关原文、用户最新反馈为输入。先还原角色、主路径、例外、数据关系和验收条件。交互草图中的样例分值、文字、ID 或模拟响应只作为具象例子，除非用户已确认为规则。
2. 区分已确认变化、待选项、现实现差异。输出最小可验收任务。每项写明现有入口或模块、行为差异、受影响契约、兼容或数据处理，以及何时算完成。
3. 用户要求实施时，按现有工程结构做小步改动。优先保留旧数据兼容与正常入口。按风险检查幂等、并发、重试、失败恢复、迁移或回滚。工程权限和提交范围沿用当前授权。
4. 代码、设计与 HTML 按实际结果对齐。通过测试只能证明覆盖的情形。没有真实联调时在交付中注明缺口。纯逆向规格或交接任务到可执行计划即可完成。

## 持续增删改

从用户指定的最新文件开始，识别受影响的图节点或链接、接口与数据、状态与验收，优先小范围修改。视觉偏好可复用，领域规则须以当前项目为准。

| 变化 | 应追踪的影响 |
| --- | --- |
| 新增功能 | 入口、职责、数据流、异常、关键验收和状态是否齐备。 |
| 修改行为 | 旧调用方与数据、状态迁移、既有样例、上下游图或文档是否受影响。 |
| 删除功能 | 入口、连接线、交叉引用、契约和验收是否成套移除。可复用历史证据有出处。 |
| 推进状态 | 写明本次完成的证据、样本和剩余阻塞，保留未实现或未验证范围。 |

当用户纠正一个具体点时，改对应源和展示。把确认的新原则放进项目已有文档或实验记录（如已建立该维护约定）。必要时用稳定标题或锚点定位内容，更新相关链接。

### 验收示例

- 初期方案要求两批材料先暂存再提交。用缺页、身份冲突和重试示例画出分流，并将真实扫描顺序标为待验证。
- 已有界面的汇总查询读取模拟数据。记为原型，并分别标明真实接口和数据验证缺口。
- 反推实现时，草图显示先保存再领下一项。任务描述包含同请求重试、保存失败保留草稿和重新获得任务的验证。草图里的示例题和分值仍是演示。
