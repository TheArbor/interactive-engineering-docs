# 通过对话研究和推进系统设计

用同一份 HTML 持续承接问题、调查、选择和实施约束。先判断用户确认了目标还是已确认具体路线。同一个需求可能有已定方向和待选实现，按各自状态处理。

## 从问题出发

1. 用用户的问题作为标题，写清要改善的结果、谁受影响、已知约束及怎样判断解决了。查现有资料、实际入口和可复核证据。只在无法查明且会显著改变选择时请用户补充，其余可逆假设标明后继续。
2. 筛选少量对结果有实质差异的可行方案。用同一场景和相同维度比，例如是否能恢复、涉及哪些组件、需要什么工具、实施代价、边界和仍待验的条件。已有方案若能满足目标，作为有意义的比较基线。材料不足时展示证据缺口和验证办法。
3. 用户希望获得判断时给出有依据的建议及适用条件。待用户作出取舍前标为「待决定」。选项可并列画成两条路、用同一输入切换结果或对照操作草图，表格只补图里看不出的取舍。

## 用户有明确方向

1. 保留用户确认的目标和关键约束，沿选定方向调查实际调用、兼容性、已有工具或外部依赖、权限、数据生命周期和可实施顺序，按当前任务选择相关项。
2. 重点查会改变实施或验收的风险。对每项记录触发条件、直接后果、预防或恢复办法，以及验证方法。按影响与证据判断是否要改变实施。发生概率未知时标待验，因果关系待证时标假设。
3. 用状态图、时序图、架构节点旁的标记或故障演练展示「在何处触发 → 用户看到什么 → 怎样处理 → 怎样验收」。来源和技术细节就近可查。发现实际硬约束时，提供证据和可行调整，由用户决定是否改变已定路线。

## 调查口径与决策落盘

- 先查会改变决策的事实，例如实际用户路径、源码入口、接口契约、日志或可重放样本。按需要核对配套工具的官方文档及版本。能低成本验证的关键差异，用同条件样例验证。分清实测、文档事实、推断和待核信息。
- 用户以对话明确选择后，在 HTML 及项目既有决策位置留痕。至少记录问题、选定方案、理由或权衡、范围与条件，以及待验证事项。同步更新受影响的流程、接口、实施顺序和验收。后续改变决定时，保留可追溯的替代关系。
- 草图里的切换、点击或预览用来试方案。正式决定以用户确认或已授权的决策记录为依据。交互演示和推荐状态按各自含义标注。

## 验收读法

业务读者能从图或操作示例看出不同选择会怎样改变自己的工作。开发读者能找到选择和风险作用在哪个环节、依赖什么、如何恢复与验证。待讨论、已有建议、已确认决定和模拟选择可清楚区分。
