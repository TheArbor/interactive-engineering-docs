# 交互式工程文档

`interactive-engineering-docs` 是一个 Codex 技能，用于把软件需求、技术方案或现有实现整理成一份可离线打开的交互式 HTML。它结合 Markdown 式查阅、轻量 PRD、可跳转的思维导图和演示式讲解，让读者顺着「目标 → 功能 → 架构 → 实施 → 验收」理解项目。也可以从已确认的 HTML 回推规格和实施任务。

## 适用场景

| 场景 | 从哪里开始 | 可以得到什么 |
| --- | --- | --- |
| 初期设计 | 需求、讨论记录或技术草稿 | 架构边界、关键流程、候选方案、待定项和验收条件 |
| 对话中研究与决策 | 用户提出的问题，或已经选定的方向 | 可操作的方案对照、实现风险、经用户确认的决策记录 |
| 记录已有功能 | 当前仓库和可核实的运行证据 | 带来源的 HTML 说明，注明哪些行为已实现、已验证或仍待核实 |
| 从 HTML 反推 | 已评审的 HTML 和相关原文 | 接口与数据约定、兼容性影响、可逐项验收的实施任务 |
| 持续增删改 | 当前文档和新的评审反馈 | 对应的图、流程、契约和验收项更新，以及状态变化的依据 |

## 安装与调用

将整个 `interactive-engineering-docs` 文件夹复制到个人 Codex 技能目录。默认目录为 `~/.codex/skills/`，配置了 `CODEX_HOME` 时使用 `$CODEX_HOME/skills/`。安装后，技能目录内应能直接找到 `SKILL.md`。

在 Codex 中用 `$interactive-engineering-docs` 调用，并提供目标、资料所在位置和本轮交付范围。

## 调用示例

**根据需求做初期方案**

> 用 $interactive-engineering-docs 把这份批量导入需求做成离线 HTML。画出组件边界和导入分流，用一个缺页示例说明阻断和恢复，标出待定项。

**根据当前实现整理文档**

> 用 $interactive-engineering-docs 从当前代码整理任务领取流程。核对入口、权限、并发和重新领取规则，注明代码证据与实际验证覆盖的场景。

**从 HTML 反推并增量修改**

> 用 $interactive-engineering-docs 根据已评审的 HTML 把「保存确认后领下一项」拆成实施任务。列出受影响的入口、接口和验收条件，再同步更新流程图和操作草图。本轮交付文档和任务清单。

## 文档原则

- **保留难以靠推断得到的细节。** 图能说清的常规步骤可省略。例外分支、恢复条件、数据归属、特殊工具和会影响效率的交互要写清。
- **让交互帮助评审。** 控件差异会影响操作时，可在同一示例中实际比较。图示可用 D2 或其他本地工具，成品默认以自包含 HTML 交付。
- **让状态有证据。** 区分设计、候选、原型、已实现和已验证，按需记录环境、样本及证据。验收条件描述可观察的结果。
- **功能一两句话，架构讲完整。** 功能摘要说清用户和结果。组件边界、数据归属、异常、先后依赖和验收在对应章节展开。
- **按问题选图。** 思维导图负责发散和记忆，概念图解释关系，逻辑树拆解问题，金字塔组织汇报和大纲。

用首次接触项目的两类读者验收。业务读者应能说明系统解决什么、有哪些功能和谁参与。开发读者应能沿核心链路指出关键业务规则、职责划分、工程逻辑、工具依赖和异常处理。

整份工程文档开工时先核对用户认可的样式和核心功能清单。架构交接和核心流程要有可见的图，并能定位到具体输入、规则和结果。缺少本轮参照时，可打开[工程文档样页](assets/engineering-doc-example.html)查看默认骨架。

## 维护与验证

修改技能后，检查入口指向的参考文件能否正常打开。用小样例验证修改涉及的工作方向。例如用有证据冲突的仓库材料验证「代码 → HTML」，用带待定项的草图验证「HTML → 实施任务」。验证生成品时，覆盖目录跳转、关键交互、宽窄视口和离线打开。
